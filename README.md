# Security of AI-Generated Web Applications

> Evaluation of the quantitative and qualitative aspects of security vulnerabilities in web applications generated by artificial intelligence.

This repository accompanies a research project for **8INF977 – Special Topic in Cybersecurity** (Université du Québec à Chicoutimi). It contains **20 e-commerce web applications generated by six different code-generating LLMs** across three technology stacks, together with a **reproducible hybrid security-testing pipeline** used to measure how many (and how severe) vulnerabilities these AI-generated applications actually contain.

All generated code and the full conversations with the LLMs are published here; the accompanying academic report describes the methodology and results in detail.

> [!WARNING]
> **These applications are intentionally unaudited AI output and contain real, known vulnerabilities** (default administrator credentials, weak password policies, client-side-only access control, outdated dependencies, stored XSS, checkout race conditions, …). They are meant to be run **locally, for research only**. Do **not** deploy them on a public server or with real user data.

---

## Research questions

The study answers three questions about AI-generated web applications:

1. **Quantitative** — Do they contain exploitable vulnerabilities, and how prevalent/severe are they?
2. **Qualitative** — Which classes of weakness recur across generations?
3. **Comparative** — Do results differ across LLM models and across technology stacks?

The yardstick is the **OWASP Top 10 (2021)** plus five complementary **CWEs** (CWE-22, CWE-98, CWE-400, CWE-362, CWE-459). Each application is an e-commerce site with a deliberately large attack surface: authentication, role-based access control, profile management, search, file uploads, server-side fetching, logging, and a simulated checkout backed by an internal account balance.

## How the applications were generated

Every application was produced in Cursor from the **same standardized sequence of
ten prompts** (Prompt 0–9), each prompt targeting specific OWASP/CWE categories:

| Prompt | Feature built | Targets |
|--------|---------------|---------|
| 0 | Project init + landing page | A06 |
| 1 | Auth, profile management, RBAC, avatar upload | A01, A04, A07 |
| 2 | Admin panel (users, products, balances) | A01, A05 |
| 3 | Product catalog (≥5 products) | A04 |
| 4 | Cart + checkout with balance check | A04, CWE-362 |
| 5 | Catalog search/filter + reviews with image | A03 |
| 6 | Server-side resource fetch (e.g. weather widget) | A10 (SSRF) |
| 7 | Internal event logging/monitoring | A09 |
| 8 | Post-purchase PDF invoice download | CWE-22, CWE-400 |
| 9 | Admin CSV product import | A08, CWE-98, CWE-459 |

The full prompt text and the complete LLM conversations are part of the project record.

## The security-testing pipeline

The pipeline combines four complementary layers so that contextual,
business-logic flaws (which generic scanners miss) are also caught:

| Layer | Tool | What it checks |
|-------|------|----------------|
| Dependency audit (A06) | `npm audit` + `pip-audit` | Known CVEs in third-party packages |
| Dynamic (DAST) | OWASP ZAP (Docker) | Baseline + authenticated active scans on the running app |
| Scripted probes | `run-manual-probes.ps1` (M1–M16) | Access control, session, injection, business logic, uploads, CWE-specific tests |
| Static (SAST, optional) | SonarQube Community (Docker) | Source-code vulnerabilities and hotspots (only with `-RunSonar`) |

### The 16 scripted probes (M1–M16)

| ID | Probe | Maps to |
|----|-------|---------|
| M1 | Admin reachable without login | A01 |
| M2 | Admin reachable as a customer | A01 |
| M3 | IDOR on profile/order IDs | A01 |
| M4 | Session still valid after logout | A07 |
| M5 | Login error allows user enumeration | A07, A05 |
| M6 | SQL injection in search | A03 |
| M7 | Stored XSS in product review | A03 |
| M8 | Checkout with insufficient balance | A04 |
| M9 | Parallel-checkout race condition | A04, CWE-362 |
| M10 | Path traversal on invoice download | CWE-22 |
| M11 | Malicious filename on upload | CWE-98 |
| M12 | Oversized file upload (≥11 MB) | CWE-400 |
| M13 | Malformed CSV import | A08 |
| M14 | SSRF via user-controlled URL | A10 |
| M15 | Failed login written to audit log | A09 |
| M16 | Temporary-file cleanup | CWE-459 |

Each probe returns **Pass**, **Fail**, or **N/A** (feature absent). Because the
FastAPI/React SPA stack serves the app shell (HTTP 200) for protected routes
while the data API still enforces authorization, a third **Weak** rating is used
for client-side-only access control.

## Quick start

### Prerequisites

- Docker Desktop
- Node.js 20+ and npm
- Python 3.11+ with `pip install pip-audit`
- PowerShell 5.1+
- Windows (the pipeline scripts are PowerShell-based)

### Run the full pipeline

```powershell
cd Cyber_Special_Project\security-pipeline
.\scripts\setup-paths.ps1     # one-time: resolve & cache the applications folder
.\scripts\run-all.ps1         # all 20 apps, sequential (~4–6 h; run overnight)
```

### Run a single application

```powershell
.\scripts\run-all.ps1 -App "Opus_NovaNest"
```

### Useful flags

| Flag | Effect |
|------|--------|
| `-App "Name"` | Run a single application |
| `-RunSonar` / `-StartSonar` | Include (and start) the optional SonarQube SAST scan |
| `-SkipDeps` / `-SkipZap` / `-SkipManual` | Skip a given layer |
| `-SkipInstall` | Skip `npm install` on app startup |

See [`security-pipeline/README.md`](security-pipeline/README.md) for full
documentation, SonarQube setup, and troubleshooting.

### Output

```text
security-pipeline/results/
├── summary.csv / summary.md      # Per-app metrics + human-readable overview
├── a06-master-inventory.csv      # All dependencies across the corpus

├── manual-matrix.csv             # M1–M16 × 20 apps
└── <AppName>/
    ├── dependencies/  zap/  manual/  logs/  (and sonar/ when -RunSonar)
```

## Key findings (summary)

- **Default credentials everywhere.** 19 of 20 applications shipped with a
  hard-coded administrator account using weak default passwords
  (`admin` / `admin123`, `Admin123!`, …), and password policies require only an
  8-character minimum with no complexity rules.
- **Automated scanners were quiet.** SonarQube findings were overwhelmingly
  code smells; OWASP ZAP raised **zero High-risk** alerts on any app — pattern-based
  SAST/DAST alone would have called all 20 apps "clean".
- **The scripted probes found the real issues.** Out of 320 probe-runs:
  **285 Pass, 18 Weak, 16 Fail, 1 N/A.** No app actually exposes admin data
  (every admin API returns 401/403, IDOR passes on all 20), but the 16 confirmed
  failures are app-specific business-logic bugs: stored XSS, checkout race
  conditions, broken server-side session invalidation, missing failed-login
  audit logging, and weak file/CSV validation.
- **Two near-universal weaknesses.** **17 of 20** apps ship high-severity (but
  non-critical, fixable) dependency advisories (A06); **all 20** expose
  Medium-severity security-header misconfigurations (A05).
- **Stack vs. model.** The technology *stack* determines the access-control
  *posture* — the FastAPI/React SPA stack systematically omits server-side route
  and session guards (a defense-in-depth weakness) — whereas the few *confirmed*
  exploitable bugs are driven by individual applications/models. Ranked by
  confirmed failures: GPT-5.5 (0) < Codex 5.3 ≈ Composer 2.5 (1) < Opus (4) <
  Cursor Pro ≈ Sonnet 4.6 (5).

**Bottom line:** AI-generated web applications in this study are less
catastrophic than expected, but far from secure. A control that merely *looks*
effective in a browser (a JavaScript redirect to login) can be bypassed by a
client that doesn't run JavaScript; only server-side enforcement on both routes
and APIs is real protection. The most prevalent weaknesses — dependency hygiene,
secure configuration, and server-side access control — are exactly the ones a
developer practising "vibe coding" is least likely to review.
